# Cloudflare Worker D1 Migration Design

## Goal

Add a Cloudflare-native backend for MoonLight Studio using Cloudflare Workers and D1 while keeping the existing Express backend available as a fallback. The migration should make the site publishable on Cloudflare with no always-on paid Node server.

## Confirmed Decisions

- Keep the existing `server/` Express/Mongo backend in the repository.
- Add a new `worker/` backend for Cloudflare Workers.
- Use Cloudflare D1 as the production database.
- Start D1 with empty content. No MongoDB data migration is required.
- Email notification is deferred to a later phase.
- Keep Cloudinary signed uploads through the Worker.
- Frontend remains Cloudflare Pages.
- Frontend API client continues to use `VITE_API_BASE_URL`.

## Non-Goals

- Do not delete or rewrite the existing `server/` project.
- Do not migrate existing MongoDB data.
- Do not implement Gmail/Resend/email notifications in this migration.
- Do not deploy to Cloudflare unless explicitly requested after code is ready.
- Do not add payment, analytics, or unrelated CMS features.

## Architecture

The repository will contain two backend implementations:

- `server/`: existing Express/Mongoose backend for fallback/reference.
- `worker/`: new Cloudflare Worker backend for production launch.

The frontend should work against either backend as long as `VITE_API_BASE_URL` points to the correct `/api` base URL.

Worker runtime:

- Hono routes.
- D1 binding for SQL persistence.
- Web Crypto for password hashing, JWT signing/verification, and Cloudinary SHA-1 signatures.
- Cloudflare Worker environment variables/secrets for JWT and Cloudinary config.

## API Compatibility

The Worker should preserve the existing frontend API shapes as closely as possible:

- `GET /api/health`
- `POST /api/auth/login`
- `GET /api/auth/me`
- `GET /api/public/brands`
- `POST /api/public/leads`
- `GET /api/public/projects`
- `GET /api/public/projects/:id`
- `GET /api/public/videos`
- `GET /api/admin/brands`
- `POST /api/admin/brands`
- `PATCH /api/admin/brands/:id`
- `DELETE /api/admin/brands/:id`
- `GET /api/admin/projects`
- `POST /api/admin/projects`
- `PATCH /api/admin/projects/:id`
- `DELETE /api/admin/projects/:id`
- `GET /api/admin/videos`
- `POST /api/admin/videos`
- `PATCH /api/admin/videos/:id`
- `DELETE /api/admin/videos/:id`
- `GET /api/admin/leads`
- `PATCH /api/admin/leads/:id`
- `GET /api/admin/users`
- `POST /api/admin/users`
- `PATCH /api/admin/users/:id`
- `DELETE /api/admin/users/:id`
- `POST /api/admin/uploads/signature`

Admin routes require a valid bearer token. Admin user management requires `owner`.

## Auth

Use Worker-compatible auth:

- Password hashing with PBKDF2 via Web Crypto.
- Per-user random salt.
- JWT signed with HMAC SHA-256 via Web Crypto.
- Token payload includes `userId` and `role`.
- Token expiry remains 7 days for compatibility.

Add a seed command or Worker-accessible script that can create/update the first owner from environment values:

- `ADMIN_EMAIL`
- `ADMIN_PASSWORD`
- `ADMIN_ROLE=owner`

## Cloudinary Signed Upload

Worker route `POST /api/admin/uploads/signature` should return the same shape expected by the frontend:

- `apiKey`
- `cloudName`
- `folder`
- `resourceType`
- `signature`
- `timestamp`
- `uploadUrl`

Sign request params with Cloudinary SHA-1 rules using Web Crypto.

## Validation And Errors

Use lightweight validation in Worker route handlers. Preserve current frontend-friendly error shapes:

- `{ message: string }`
- Optional `errors` array for validation details where practical.

## Deployment Docs

Add docs for:

- Creating D1 database.
- Applying migrations.
- Configuring Worker bindings/secrets.
- Seeding the owner.
- Setting `VITE_API_BASE_URL` to the Worker API URL.
- Keeping `server/` as fallback only.

## Verification

Before completion:

- Worker type check/build passes.
- Unit tests for auth crypto helpers pass.
- Unit tests for Vimeo normalization and Cloudinary signing pass.
- Existing client tests pass.
- Existing client build passes.
- Existing server tests/build may remain passing; do not break `server/`.

## Success Criteria

- `worker/` contains a deployable Cloudflare Worker backend.
- D1 migrations define the required CMS schema.
- Frontend can target Worker API through `VITE_API_BASE_URL`.
- Owner can seed/login/manage CMS data on empty D1.
- Public pages can read brands/projects/videos/leads from Worker routes.
- Admin CMS can manage brands, projects, videos, leads, and admin users against Worker routes.
- Cloudinary signed upload route works without Node APIs.
- Existing `server/` backend remains in the repo and buildable.
